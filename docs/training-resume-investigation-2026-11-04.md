## 2. 明确发现并处理的问题

### P0：没有完整续训状态，长时间运行的损失不可控

新增 `training_checkpoint.py`：

- 存模型、Adam、内参/曝光、每帧所属场、混合权重、细化/上采样/alpha mask 调度、数据活动和预读边界、添加帧计数、下一步编号、Python/NumPy/PyTorch CPU/训练设备 CUDA RNG。
- 默认开始时、每 1000 完整步、切场和结束保存。SIGINT/SIGTERM 请求完整步边界保存；OOM 不尝试保存半更新状态。
- 同目录临时文件、flush/fsync、原子替换。磁盘写入失败仍保留上一份有效 `resume.th`；硬中断可能留下临时文件/孤立分片，不自动删除已有实验数据。
- 冻结场各存一次、周期保存活动状态；`resume.th` 引用 `resume_fields/`，两者必须一起备份。恢复时历史场保留在 CPU。迁入新空目录会为历史场重新生成独立分片，不依赖旧目录的寿命。
- 自动恢复原始参数，只应用一次速度因子，拒绝更改损失/场/窗口等训练配置。允许调整设备/batch/日志频率，以及校验一致的输入路径迁移。记录每次启动的原始和有效参数。
- 旧渲染 checkpoint/日志不冒充可续训存档，最终渲染输出兼容旧接口。

### P1：场切换期间旧 Adam 状态释放过晚

旧 `append_rf()` 将旧场移动到 CPU 后，先构造新场，再替换 `rf_optimizer`。这意味着新场分配期间仍持有旧场的 GPU Adam moments。现在先清空旧场梯度、释放旧 RF optimizer 和冻结位姿不再使用的 moments，再分配新场。测试检查新场构造发生之前，旧 optimizer 已不存在、旧 pose optimizer state 已释放。

这是**确定存在的瞬时峰值风险**，不是“所有旧场一直在 GPU 上”的证据。旧代码本来就会将历史场移到 CPU；不能以“105 个场”直接断言有 105 个全分辨率场常驻显存。本机没有实际 GPU 峰值对照，不报告虚构的显存节省量。

### P1：关闭 LR reset 后，上采样优化器指向旧参数

`upsample_volume_grid()` 替换参数对象。旧逻辑仅在 `lr_upsample_reset=1` 时重建 Adam；设为 0 后，优化器仍持有旧张量，新网格无法被正常更新。现在两种情况都会重建 Adam，关闭 reset 时保留各组学习率，形状改变后不保留不兼容的 moments。新增回归验证新参数确实得到更新。

本地 100 帧 checkpoint 记录 `lr_upsample_reset=1`，因此这个分支 bug **不能解释该实验的深度回退**；211/223 实际配置未知。

### P2：历史场边界每步重复记录、绘图与进度频率耦合

旧循环每步为每个历史场写两个 scalar。105 场时，仅边界就有 210 条 scalar/步；93 场时是 186 条/步，还未计损失与图片。现在每步只记当前场，切场时补记刚冻结场最终边界；不再反复写不会变化的历史数据。

位姿图片改由独立 `pose_vis_every` 控制（默认 2000，0 关闭），不再跟随默认 200 步的控制台刷新频率。保留损失与梯度日志；新资源标量记录 CUDA allocated/reserved/间隔峰值/剩余量和场数。

这些改动减少重复 I/O 和绘图，不等于已证明原先 OOM 是日志引起的；`draw_poses()` 本来就会关闭 figure，未发现这里有未关闭 figure 的直接证据。

## 3. 仍需服务器定位的资源风险

1. **磁盘空间**：附件检查时 `/mnt/data` 显示约 32 GB 可用、使用率 100%。这是当时的容量记录，不是当前容量。新增存档不能解决磁盘不足。原子覆盖需要同时容纳旧存档和临时新存档；新冻结场还需额外分片空间。最终完整 `checkpoints.th` 会再占一份全模型空间。
2. **主机 RAM/磁盘随场数增长**：历史场仍在 CPU 内存中，没有实现磁盘换入/换出。已有 4 场完整 checkpoint 为 1,154,903,306 B；若粗略假设每场体积相同，105/93 场仅完整模型约为 30.3/26.9 GB（十进制），只是容量估算，不是中断实验的实际模型大小。不要因为显存释放了就忽略 RAM、swap 与保存空间。
3. **高分辨率与采样**：本地 100 帧最终网格为 640³、step_ratio=0.5。升网格、生成 alpha mask、前向/反向射线采样和梯度诊断都有临时分配；需用 traceback 和资源曲线对齐具体步骤。梯度诊断对多个损失额外反传，不能把 `grad_log_every=20` 当成免费操作。
4. **恢复与离线渲染有区别**：本补丁续训恢复只把当前场放到训练设备。现有 `render.load_model()` 仍将完整渲染模型放到目标设备；几十至上百场 GPU 渲染可能先在加载阶段 OOM，降低 `ray_chunk` 不能解决模型常驻问题。此独立渲染大规模问题尚未修改，可先用 CPU 或另行实现按需场加载。
5. **外部 GPU 竞争**：附件进程列表出现其他训练进程，但没有这些进程的 GPU 归属、显存或对应时间，不能认定它们导致此次 OOM。下次保留 `nvidia-smi`、完整 stderr、代码 commit 与参数，并优先用一个短片段验证切场/保存/恢复后再启动整段。

建议下次失败至少保留：OOM traceback（失败算子/申请大小）、`run_history.jsonl`、`resume.th` 及分片、TensorBoard 资源日志、训练 stdout/stderr、GPU 型号和其他占用、磁盘与 RAM 状态。`batch_size` 可在恢复时降低，但会改变采样和优化轨迹，不应将不同 batch 的结果视为严格重复试验。

## 4. 本地已有日志复算：深度后期回退

100 帧实验共 47,885 步，4 场；已有 scalars.npz 所有值有限。本次从数组重算各场最佳连续 500 步与末 500 步：

| 场 | 最好 500 步深度 L1 / m | 最后 500 步 / m | 回升 | 最好深度窗口的 RGB 项 | 最后 RGB 项 |
|---|---:|---:|---:|---:|---:|
| RF0 | 0.16327 | 0.19198 | 17.58% | 0.010941 | 0.008963 |
| RF1 | 0.13650 | 0.16413 | 20.24% | 0.009400 | 0.008251 |
| RF2 | 0.14333 | 0.16817 | 17.32% | 0.009486 | 0.008229 |
| RF3 | 0.15613 | 0.17689 | 13.30% | 0.009470 | 0.008097 |

RGB 项已含 0.25 系数。step>1000 的已记录梯度中，加权深度/RGB 的 L2 比值中位数：密度约 0.249、旋转 0.0614、平移 0.0443。该实验 `depth_weight=0.001`，这些值不支持“深度长期压倒所有梯度”的判断；但不同参数组的数值不能直接相加比较。

这是一种重复出现的 RGB/深度优化权衡线索，不能直接证明哪项损失有 bug，也不能推导真实轨迹准确率。随机 batch 500 步均值不是同一组像素的固定评测；改变窗口内容也会影响曲线。

已有图像报告指出训练视图平均 SSIM 0.5790，帧 54 最低，50–54 的 PSNR 下降约 1.14 dB，位于 RF1/RF2 交接附近。这些是已有报告的值，**本次未重新渲染或复算 SSIM**。应进一步在同一帧、同一位姿分别渲染两个场和混合结果，而不是直接宣布“接缝 bug”。训练只监督当前场，最终混合视图可能与训练 loss 所见预测不同。

下一步算法对照优先级：固定像素的阶段性 RGB/深度验证；固定 tracking 位姿与联合 BA 同预算对照；交接两侧独立渲染。不要先盲目加迭代或把深度权重从 0.001 提到 0.1。
